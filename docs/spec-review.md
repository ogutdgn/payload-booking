# Spec review — PLUGIN_BOOKING_SPEC.md

Date: 2026-09-15. Reviewed spec: the version at the repo root, before any code exists.

Method: seven independent reviewers (Payload API, concurrency, time/DST, security, packaging, admin/frontend, product consistency), then a merge pass, then every finding was handed to one or two adversarial verifiers whose job was to refute it, then a completeness critic. 112 agents in total. Claims were checked against Payload 3.84.1 source installed by the official plugin template (`create-payload-app -t plugin`, scaffolded today), Payload's reference docs, and scripts that were actually run against MongoDB (mongodb-memory-server replica set) and the local PostgreSQL 17.

Result: 76 findings kept (1 blocker, 27 major, 42 minor, 6 nit), 0 refuted, 1 contested and downgraded. 93 spec statements verified correct (listed at the end).

## Verdict

The design is sound. Every core idea held up under test: database-level uniqueness through a Payload `unique` text field, the hook-derived lock key with the `originalDoc` merge, the pure `core/` with an injected `now`, server-side time in the business zone, and the file layout matching the official template. The race test passes on both adapters. The problems are in Payload mechanics the spec assumed rather than checked, and in cross-section consistency (fields used in one section and never declared in another). None of them needs a redesign. All fixes are local.

## The ten facts that change the plan

1. **Mongo breaks the null lock key (F01, blocker).** A sparse unique index still indexes an explicit `null`, and Payload's Mongo adapter always writes the null. The second cancellation in the whole system fails. Fix: write a per-document tombstone `released#<id>` instead of null. Verified on both adapters.
2. **`pnpm link --global` no longer exists (F02).** pnpm 11+ removed it, and `pnpm add file:../dir` skips `publishConfig`, so exports would point at `src/`. The only correct local flow is `pnpm pack` then `pnpm add ../<tarball>.tgz`.
3. **The template does not install on pnpm 12 as generated (F05).** `pnpm-workspace.yaml` ships `allowBuilds` placeholders; install exits 1 until they are set.
4. **There is no post-commit hook in Payload (F21, F03).** `afterChange` and `afterOperation` both run before `commitTransaction`. Emails, `emailLog`, and `onAppointmentChange` must be sent by endpoint code after `await payload.create/update` resolves. A manual status edit in the admin therefore bypasses the cancel path unless blocked by a validator.
5. **On Mongo with transactions, the race loser is a `WriteConflict` (code 112), not a `ValidationError` (F16).** The seat loop must call `payload.create` with `disableTransaction: true` and must never share a `req` that carries a transaction (F17).
6. **`payload.find` defaults to `limit: 10` (C01).** The availability query needs `pagination: false` or it undercounts after ten bookings in the window.
7. **The dashboard widget must be a server component from a `./rsc` entry (F08).** A `'use client'` `beforeDashboard` component receives no `payload` prop. The export map needs `.`, `./client`, `./rsc`, `./react`, `./styles.css`, each declared in `exports`, `publishConfig.exports`, and `dev/tsconfig.json` paths.
8. **The peer block is wrong (F04).** `@payloadcms/ui` has only ever accepted React 19 and pins `payload` exactly; `trash` needs payload 3.49+. Use `payload ^3.84.1`, `@payloadcms/ui ^3.84.1`, `react`/`react-dom ^19`, no `next` peer.
9. **The template's test bench is Mongo in-memory, not Postgres (F07, C11).** The dev app must select the adapter from env, run integration tests on a dedicated Postgres database that starts clean, and keep a Mongo parity suite. CI runs both.
10. **No option supplies the public site origin (F22).** Payload's `serverURL` defaults to empty, so the cancel link in the email would be relative. Add `siteUrl`.

## Findings in detail

Each entry: the verified claim (as corrected by the verification pass) and the concrete spec change. IDs prefixed C came from the completeness critic. F18 was contested (one verifier refuted it as already covered); it is kept as a minor clarification.

### F01 · blocker · §8 (also §2.7, §3.4, §16 'cancel frees the slot') — slotLockKey = null on cancel collides on MongoDB: second cancel fails

Kind: wrong. Found by: payload-api, concurrency, product-consistency.

**Claim.** §8 frees a slot by writing slotLockKey = null and assumes Mongo's sparse unique index ignores it. The adapter does create the index as sparse+unique, but MongoDB sparse indexes still index documents whose field exists with an explicit null, and Payload's mongoose adapter always writes the null as a present field ($set; there is no config path to $unset). Verified on Payload 3.84.1 + db-mongodb: book → cancel → rebook → second cancel throws ValidationError (path slotLockKey); any create where the hook yields null also collides with the first cancelled row. Only the very first cancellation in the whole system succeeds on Mongo, so §2.2 cancel, §2.7 (works on both adapters) and §3.4 ("unique: true ... which both adapters honour") are violated. Postgres is unaffected (NULLs are distinct).

**Fix.** Never write null to slotLockKey. In the collection beforeChange hook, when the merged status is not in ACTIVE_STATUSES (or deletedAt is set), set data.slotLockKey = `released#${originalDoc?.id ?? crypto.randomUUID()}` (a per-document, non-colliding tombstone; on update the id is available, on create the doc is normally active). Keep required: false on the field. Rewrite §8's "cancelled → NULL → slot freed" and the "NULL is distinct in Postgres … on Mongo confirm the adapter creates the unique index as sparse" sentences to state the released#<id> rule and note explicitly that sparse does NOT exclude explicit nulls. Add to §16 integration tests, run on BOTH adapters: book → cancel → rebook → cancel again (idempotent second cancel), plus "cancel two appointments for the same slot", and assert that re-confirming a cancelled appointment while the slot is taken is refused with a ValidationError on slotLockKey.

### F03 · major · §2.2 / §6.4 / §10 / §13 — Editing status to 'cancelled' in the admin form bypasses the cancel code path

Kind: inconsistent. Found by: concurrency, product-consistency, security.

**Claim.** Editing `status` to 'cancelled' in the admin edit view, bulk-edit, or via PATCH /api/appointments/:id (all allowed by §6.4's `update: options.access.manage` and an unrestricted select) runs only the §8 lock hook: the slot is freed but no customer/business email, no emailLog entry, no cancelledAt/cancelledBy, and no `onAppointmentChange` fire, because §5/§10 place those after commit and Payload 3.84.1 has no post-commit hook (updateByID.js runs afterOperation before commitTransaction). `admin.readOnly` is UI-only in Payload (never checked server-side), so §6.4/§13 as written cannot honour §2.2's "one code path" nor guarantee §20 #4 ("staff cancel; the customer is emailed").

**Fix.** Write into §6.4 and §13: (a) `status` gets a `validate(value, { previousValue, operation, req })` that returns 'Use the Cancel button so the customer is notified.' when `operation === 'update'`, `value === 'cancelled'`, `previousValue !== 'cancelled'` and `req.context?.bookingCancel !== true`; `completed`/`no-show` remain editable. (b) The two cancel endpoints call `payload.update({ ..., context: { bookingCancel: true }, req })` (Local API copies `context` onto `req.context`, createLocalReq.js:86). (c) `cancelledAt`, `cancelledBy`, `cancellationReason` and `emailLog` get `admin.readOnly: true` plus `access.update: ({ req }) => req.context?.bookingInternal === true` (field access is skipped under `overrideAccess: true`, so endpoints can still write them; admin PATCHes cannot). (d) State explicitly that emails, emailLog appends and `onAppointmentChange` are triggered only from plugin endpoints after the Local API call returns (i.e. after commit), and add an integration test: PATCH status→'cancelled' via REST as staff returns 400 with that message, while POST /appointments/:id/cancel succeeds and emails. Alternative if the owner prefers status to stay editable: an afterChange hook detecting confirmed→cancelled that runs the shared cancel routine, accepting that the email sends inside the transaction (ADAPTERS.md:50-60) and can race a rollback.

### F04 · major · §3.2 — Peer range payload ^3.37.0 is unsupportable; React 18 and next claims are false

Kind: wrong. Found by: payload-api, packaging.

**Claim.** The §3.2 peer block is wrong on three counts: (1) `payload: ^3.37.0` covers versions that lack `CollectionConfig.trash` (absent in 3.37.0 types; added in 3.49.0, #12656) while §6.4 uses `trash: true`, and the spec's own test policy (line 101) never exercises anything below the template's 3.84.1; (2) `react`/`react-dom` `^18.0.0 || ^19.0.0` is a false contract because the admin components must import `@payloadcms/ui`, which has only ever accepted React 19 (3.37.0: `^19.0.0 || ^19.0.0-rc…`; 3.84.1: `^19.0.1 || ^19.1.2 || ^19.2.1`); (3) `next ^15.0.0 || ^16.0.0` is wider than the range @payloadcms/ui and @payloadcms/next actually support (`>=15.2.9 <15.3.0 || >=15.3.9 <15.4.0 || >=15.4.11 <15.5.0 || >=16.2.2 <17.0.0`), and a `next` peer is unnecessary if no plugin source imports `next/*`. The official template declares only `{ payload: "^3.84.1" }`.

**Fix.** Replace the §3.2 block with `"peerDependencies": { "payload": "^3.84.1", "@payloadcms/ui": "^3.84.1", "react": "^19.0.0", "react-dom": "^19.0.0" }`, stating the rule "floor = lowest Payload version CI actually runs; bump the floor whenever a newer Payload feature is used". Keep `@payloadcms/ui`'s range identical to `payload`'s because `@payloadcms/ui` pins `payload` exactly, and add a README note that hosts must keep every `@payloadcms/*` package on one version (§17 step 3 already checks for a single `@payloadcms/ui` copy). Drop `next` and `@payloadcms/next` from the peer list unless a source file imports them; if a `next` peer is ever required, copy `@payloadcms/ui`'s range verbatim instead of inventing one. Optionally add a comment that `trash: true` (§6.4) requires payload >= 3.49.0, which the ^3.84.1 floor already satisfies.

### F05 · major · §4 — Template does not install on pnpm 12 as generated

Kind: wrong. Found by: packaging.

**Claim.** The official plugin template, as generated today, does not install cleanly under the owner's pnpm 12.3.4: `pnpm install` exits 1 (ERR_PNPM_IGNORED_BUILDS for @swc/core and mongodb-memory-server) because pnpm >=11 ignores package.json#pnpm.onlyBuiltDependencies and the generated pnpm-workspace.yaml leaves `allowBuilds` placeholders while strictDepBuilds defaults to true; engines.pnpm "^9 || ^10 || ^11" also excludes pnpm 12 (not enforced since engine-strict is unset). Spec §4 says "scaffold and keep it" but omits this mandatory fixup, so the first local install and the prescribed CI workflow both fail. (kind: missing, not wrong)

**Fix.** Add to §4 a "first commit after scaffolding" step: replace pnpm-workspace.yaml with `allowBuilds: { '@swc/core': true, esbuild: true, mongodb-memory-server: true, sharp: true, unrs-resolver: true, workerd: true }` (or run `pnpm approve-builds` and commit the result), delete the `pnpm` block from package.json, set `"packageManager": "pnpm@12.3.4"` and `"engines": { "node": ">=20.9.0", "pnpm": ">=10" }` (next 16 needs node >=20.9.0; vitest 4 needs ^20 || ^22 || >=24), and pin the same pnpm major in .github/workflows/ci.yml (e.g. pnpm/action-setup reading packageManager) so CI, the plugin repo and the client repo agree.

### F06 · major · §4 / §16 — tests/int cannot resolve @payload-config; vitest runs int files in parallel

Kind: wrong. Found by: packaging.

**Claim.** §4's `tests/int/` layout is not wired by the template: vite-tsconfig-paths only applies a tsconfig's `paths` to importers located under that tsconfig's directory, so `@payload-config` (defined in dev/tsconfig.json, used by the template's own dev/int.spec.ts) is unresolvable from tests/** — and, contrary to the intuitive fix, widening dev/tsconfig.json's `include` to ../tests does NOT help. Neither tsconfig type-checks tests/**, so a CI "typecheck" step would skip the specs. Separately, vitest 4 runs spec files in parallel by default and @payloadcms/db-postgres runs pushDevSchema on every getPayload() outside production, so several int files against the one Postgres database in §16 would push schema and run the seed concurrently, making the race test flaky. (Kind: missing/risk rather than wrong — the spec does not assert how the alias is wired; also note the template's dev config is Mongo-memory under NODE_ENV=test, not the Postgres §16 assumes.)

**Fix.** Recommended default: keep integration specs where the template already wires them, `dev/int/*.spec.ts` (or `dev/*.int.spec.ts`), and put pure unit specs beside their modules as `src/core/*.spec.ts`; drop `tests/` from the §4 tree. If the owner insists on `tests/`, do NOT edit dev/tsconfig.json's include (verified ineffective); instead either import the config relatively (`../../dev/payload.config.js`, verified working with zero config), or add `resolve.alias['@payload-config'] = dev/payload.config.ts` in vitest.config.js, or add a `tests/tsconfig.json` with its own `paths` (both verified). Split vitest with `test.projects`: `unit` (src/**/*.spec.ts, parallel, no env) and `int` (dev int specs, `fileParallelism: false`, `loadEnv(dev)`), and have int specs share one `getPayload` per file with a unique DATABASE_URI per CI job (or a single global setup) so only one dev-schema push touches the database. Add `"typecheck": "tsc --noEmit -p dev/tsconfig.json"` (verified: exits 0 on the template) so dev/ specs and src/ are type-checked in CI; if tests/ is kept, include it from that tsconfig. Also reconcile §16 with dev/payload.config.ts: switch the dev app to postgresAdapter (DATABASE_URI) or state explicitly that int tests run on Postgres via a separate config.

### F07 · major · §4 / §16 — Dev app is Mongo-memory while spec says Postgres; concrete DB strategy missing

Kind: decision. Found by: payload-api, packaging.

**Claim.** §16 states integration tests run "against a real Postgres (the template's dev app config)", but the official template's dev config is mongooseAdapter + a MongoMemoryReplSet under NODE_ENV=test, and vitest forces NODE_ENV=test, so `pnpm test:int` as scaffolded runs on in-memory Mongo, not Postgres. The spec never says how Postgres is wired for dev/int/CI. The Postgres facts that must shape that decision: db-postgres auto-creates a missing database, pushes schema via drizzle whenever NODE_ENV !== 'production' (push defaults on), and pushDevSchema opens a `prompts` confirm when drizzle-kit reports warnings (table/column delete, type change, add not-null) — verified to block forever on a non-TTY/closed stdin, i.e. it hangs CI or any reused local DB after a destructive schema change. On the Mongo side, a fresh replica set with versions enabled fails the first write(s) with transient 'Unable to acquire IX lock' / 'catalog changes' errors, and under transactions the race loser surfaces as MongoServerError code 112 WriteConflict rather than a ValidationError on slotLockKey, so a Mongo parity race test needs a warm-up and different assertions.

### F34 · minor · §6.3 blackout beforeChange guard — Guard query shape unspecified; race with in-flight bookings
